# Brief: ActiveAI

## 1. Concept Name

ActiveAI

## 2. One-Sentence Description

A Rails-native Ruby gem that gives LLM calls a declared, testable home — with a built-in agentic loop, multi-agent workflows, provider abstraction, streaming, and full Rails instrumentation — following the same conventions Rails developers already know.

## 3. Target Audience

Rails developers and engineering teams building AI-powered applications who want LLM calls to feel like a first-class Rails citizen — not a Python library bolted on. They already know ActionMailer and ActiveRecord. They want generators, `config/ai.yml`, and `ActiveSupport::Notifications`. They are not building fully autonomous agents; they are building human-in-the-loop workflows where AI assists and the developer controls the architecture.

## 4. Core Insight

Every other Ruby AI library makes you write the plumbing. ActiveAI gives you the plumbing and the conventions. Just as ActionMailer didn't make sending email easier by wrapping SMTP differently — it made it easier by giving email a *place in your app* — ActiveAI gives LLM calls a place: generators to scaffold them, `config/ai.yml` to configure them, `ActiveSupport::Notifications` to observe them, and a class hierarchy that keeps individual agents declarative and thin. The insight is architectural, not technical: LLM calls don't need a better API wrapper, they need a home.

## 9. Competitive Landscape

**Closest alternatives:**

- **langchainrb** (patterns-ai-core, ~2k GitHub stars) — the most prominent Ruby LLM library. Generic chain/agent abstraction ported from Python's LangChain. Not Rails-first: no generators, no `config/ai.yml`, no `ActiveSupport::Notifications`, no controller mixin. Works in any Ruby context, which means it fits no context particularly well.
- **ruby_llm** (Carmine Palino) — gaining traction in the Rails community for simple chat and image integration. Easier drop-in than langchainrb, but scoped to single-turn conversations. No agentic loop, no workflows, no memory pipeline, no orchestration.
- **Direct SDK gems** (ruby-openai, anthropic gem) — low-level API wrappers. You write the agentic loop, tool dispatch, streaming, memory, error handling. Everything. ActiveAI is what you'd build on top of these.
- **Managed services** (AWS Bedrock Agents, GCP Vertex AI Agents) — cloud-hosted. Vendor lock-in. No Rails conventions, limited observability, black-box memory, markup on LLM costs.

**White space:** No Ruby library gives you all five together — generators, Rails config conventions, ActiveSupport instrumentation, multi-agent workflows + orchestration, and a persistent memory pipeline. Every existing option picks 1-2. ActiveAI picks all five, and grounds them in the Rails conventions developers already know.

## 10. Speculative Elements

- **Memory pipeline consolidation** — The `ConsolidateJob` / `ConsolidationAgent` (weekly scheduled) that detects relationships between memories is architecturally specified but described as active development. The spec page should frame this as "pipeline design" not "proven production feature." The `PersistJob` and `EmbedJob` are further along.
- **"Battle-tested" claim** — ActiveAI was extracted from writer-v3 (a real production writing app). The extraction is recent; the gem's public API is still stabilizing. "Extracted from production use" is accurate; "production-ready gem" requires the caveat the README already includes.
- **Provider-agnostic switching** — Changing `provider :openai` to `provider :anthropic` works at the framework level. Whether a specific agent's prompts translate cleanly across providers is application-specific. The page should be clear that the *framework* is provider-agnostic, not that switching is zero-effort at the prompt level.
