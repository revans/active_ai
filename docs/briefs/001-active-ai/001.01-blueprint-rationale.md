## Key Design Decisions

### 1. Primary color: `#5B8DBE` — muted steel blue

The banned palette for this category is the Tailwind indigo/violet cluster (`#6366f1`, `#8b5cf6`): it's what every AI startup uses and communicates nothing. The alternative is to ask what color this specific audience already associates with trusted tools.

Rails developers spend most of their working hours in three environments: GitHub (`#58A6FF` on dark), VS Code (various steel blues), and their own terminal (typically cyan-adjacent accents). The color that says "developer tool" to them lives in the HSL 205–215° range at medium saturation — not the saturated `#3b82f6` (too bright, startup feel) and not `#6366f1` (too purple, AI startup feel).

`#5B8DBE` lands at HSL 210°, ~40% saturation: muted enough to read as "restrained professional tool," cool enough to communicate precision, familiar enough that the audience doesn't notice it consciously — which is what a good tool primary should do. Contrast against `#0D1117`: ~5.6:1, WCAG AA.

### 2. Background: `#0D1117` — not pure black, not deep navy

The Point's default dark is `#0a1628` — a deep navy with strong blue undertones. That palette is designed for a "blueprint drawing" atmosphere where the blue reads as drafting paper. For ActiveAI, that reads as "The Point demo site," not "a gem that belongs in your Rails app."

GitHub's dark background is `#0D1117` — a near-neutral dark with no dominant hue. This is the surface Rails developers already associate with serious open-source tooling. Using it creates immediate environmental familiarity: the developer sees the page and their brain reads "this is in my world." That's not brand theft; it's cultural legibility.

Pure black (`#000`) is avoided because it reads as void — the eye has no surface to land on and contrast becomes harsh. GitHub-dark is the precise calibration: professional, not austere.

### 3. Grid re-keyed to steel blue at 5%/9%

The Point's blueprint grid is kept because it earns its place: it communicates "technical drawing, structured, engineered" without saying it. The default grid uses `#3b82f6` at 8%/15% — the blueprint accent blue, which on `#0D1117` (no blue undertone) reads as deliberately colored rather than textural.

Re-keying to `rgba(91, 141, 190, 0.05)` / `rgba(91, 141, 190, 0.09)` achieves the same engineering-graph-paper texture at opacity levels that disappear when you're reading but orient the space when you're scanning. The hue now matches the brand primary — visual coherence over mere texture.

### 4. Type: geometric-sans at 500 (default Inter, no override)

The brief says "sharp and geometric — modern, precise." The Point's default is Inter, which is exactly this. No override is needed — the decision is to accept the default deliberately, not by neglect.

Weight 500 (medium) replaces The Point's default 600 (semibold). A 600-weight heading at this scale starts to feel promotional; 500 says "the author trusts the content." A senior engineer explaining a gem doesn't raise their voice. The type weight is the voice.

`--font-mono` is not overridden because JetBrains Mono is already The Point's default monospace, loaded in base.css. This is another deliberate default: JetBrains Mono was designed specifically for long-duration code reading, distinguishes similar characters (0/O, 1/l/I), and is what VS Code users already have as their preferred font. It requires no defense.

### 5. Motion: surgical (0.05s/0.1s/0.15s, easing: ease throughout)

The three animated SVG flow diagrams are **content animations** — they demonstrate how the agentic loop cycles, how deterministic and LLM-driven workflows compare, how the memory pipeline stages sequence. They run as self-contained SVG/CSS sequences using the `--active-ai-flow-*` tokens defined in brand.css.

UI motion (hover states, focus rings, nav transitions) is surgical: 50ms fast, 100ms base, 150ms slow, no bounce. The page should feel like a terminal responding to a command — instant, clean, no personality injected into the feedback. Motion that calls attention to itself in a developer tool says "I don't trust you to understand what just happened."

`--easing-smooth: ease` is set explicitly (required companion to surgical fast/slow, prevents asymmetric hover states that read as browser inconsistencies).

### 6. Shape: `--radius: 0px` — no compromise

Every rounded corner softens. This library has no rounded corners in its codebase. The code blocks are rectangular. The generator output is rectangular. The `config/ai.yml` file is structured. The page should be too.

The only place where soft radius would be considered is inline badges (`.active-ai-badge`) — and they're also `border-radius: 0`. This is not aesthetic stubbornness; it's formal consistency. A badge with rounded corners on a page of sharp code blocks reads as an import from a different product.

### 7. Amber for tool-call nodes (`#D97706`) — visual language inheritance

The vocabulary spec's observability/tracing mockup section recommends amber (`#D97706`) for tool call spans. This has been carried into the brand tokens (`--active-ai-node-tool-stroke`, `--active-ai-node-tool`) so the three SVG flow diagrams can use consistent color semantics: blue = LLM/agent calls, amber = tool executions. This distinction mirrors how developer observability tools (Datadog, Honeycomb, Langsmith) color their trace spans — the audience will read it correctly without a legend.

### 8. Surface step-up as depth system (`#0D1117` → `#161B22` → `#1C2128`)

Dark theme + depth = subtle is the vocabulary rule: shadow values are invisible on dark surfaces; depth comes from surface color contrast. The three-step palette (`--color-bg`, `--color-surface`, `--color-surface-elevated`) matches GitHub's exact dark surface system.

This is also practical: a developer seeing this page is already reading GitHub daily. When a card lifts off at `#161B22` against `#0D1117`, their visual system reads the separation immediately — not because of training data, but because it's the same distinction they use to read GitHub's repository cards from their backgrounds. Cultural pattern inheritance.

## What was straightforward

- Density (compact) and compositional mode (functional): unambiguous for a developer evaluating a library.
- Type family: default geometric-sans is correct; no decision required.
- Monospace: JetBrains Mono is The Point's default and the right choice; no override needed.
- Shape (sharp): zero ambiguity. Developer tools are structured.
- Motion (surgical): zero ambiguity. Developer tools don't perform.
- Theme (dark): required by the brief; also the industry default.
- Layout pattern (document): developer evaluates, doesn't browse. Text-led single column.

## What required non-obvious decisions

- **Primary color**: The brief says "muted electric blue or cool indigo" — deliberately avoiding both the standard The Point blueprint blue (`#3b82f6`) and the banned AI startup indigo range. Landing on `#5B8DBE` required reasoning from what this audience stares at in their tools, not from category convention.
- **Background `#0D1117` vs. The Point dark `#0a1628`**: Explicitly replacing the system default. The Point's navy dark is beautiful but reads as "demo." GitHub-dark reads as "deployment."
- **Grid re-keying**: The `--bp-grid-*` tokens are normally set in base.css and not mentioned in brand.css. Overriding them here is non-standard but necessary — the default blue grid on a neutral dark background creates hue conflict, not texture.
- **Amber for tool nodes**: Not in the brief, derived from the vocabulary spec's observability pattern. Applied proactively based on the brief's description of tool dispatch in the agentic loop diagrams.
- **Surface palette from GitHub (not from The Point's navy system)**: When the background is `#0D1117` instead of `#0a1628`, The Point's default `--bp-surface: #1a2d4a` (strongly blue-navy) would clash. Replacing with GitHub's neutral surface (`#161B22`, `#1C2128`) maintains coherence.
- **Weight 500 vs. 600 default**: Subtle but intentional. 600 is The Point's default (semibold). 500 changes the register from "confident heading" to "measured explanation." For a library that earns trust through architecture, not volume, that's the right register.

## Reviewer: verify these specifically

- `--radius: var(--bp-radius-none)` is used instead of `0px` directly to stay within the Point token system. Verify `--bp-radius-none` is defined in base.css (it is, at `0`) and that the reference resolves correctly in `@layer brand-state`.
- The `.active-ai-analogy-table` width distribution (`td:first-child: 40%`) is a judgment call. If the "Rails" column items are significantly longer than the "ActiveAI" items, the ratio should shift to 50/50.
- Amber `#D97706` for tool-call node borders was derived from the vocabulary observability spec, not from the brief. Verify this reads as intentional (not accidental) against the steel-blue primary on dark surfaces.
- The `--bp-grid-color` and `--bp-grid-color-bold` overrides in `brand-state` layer: confirm these tokens propagate to the `body` background-image gradient (defined in base.css outside any layer). Since the body rule uses CSS custom properties, the layer override should cascade — but verify.
- `.active-ai-codeblock border-left: 3px solid var(--color-primary)`: combined with `border: 1px solid var(--color-border)`, this creates a visual hierarchy issue on the left edge (1px border + 3px override = effectively 3px left, 1px other three sides). This is intentional (left-accent pattern common in IDE and documentation UIs) but verify it renders as expected and doesn't feel asymmetric at narrow widths.
